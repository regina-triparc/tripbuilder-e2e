# tripbuilder-e2e

Playwright end-to-end tests for TripBuilder, run against the deployed portal
(`https://tripbuilder-portal-gmguhndwguh2fxh6.a03.azurefd.net`). No localhost
dev servers are needed.

This repo has two kinds of tests:

| Folder | Written by | Playwright project |
|---|---|---|
| `e2e/ui`, `e2e/api`, `e2e/pdp`, `e2e/services`, `e2e/traveler` | people | `ui`, `api`, `pdp`, `services-hotel`, `traveler`, ... |
| `e2e/qa/<TICKET>.spec.ts` | the [TB-TAF](https://github.com/regina-triparc/TB-TAF) QA agent, one file per Jira ticket | `qa-agent` |
| `xray/<TICKET>/` | the same agent: the ticket's Xray test cases (JSON, CSV, readable plan), exported to Jira after review | - |

It started as `apps/search-e2e` in a local TripArc.TripBuilder checkout and moved
here so the suite and the generated tests are versioned and shared.

## Setup

```bash
git clone https://github.com/regina-triparc/tripbuilder-e2e.git
```

```bash
cd tripbuilder-e2e
```

```bash
npm ci
```

```bash
npx playwright install chromium
```

```bash
cp .env.example .env
```

On Windows PowerShell use `copy .env.example .env`. Fill in `TBA_E2E_EMAIL` and
`TBA_E2E_PASSWORD` with your own UAT test login (see [Auth](#auth)). Every other
variable is optional and its tests skip when it is unset.

```bash
npx playwright test --project=setup
```

signs in once and saves the session to `e2e/.auth/state.json` (git-ignored).

## Tests generated by the QA agent

The TB-TAF service writes `e2e/qa/<TICKET>.spec.ts` and runs it with the
`qa-agent` project, which reuses the signed-in session from `setup`. With
TB-TAF in managed-clone mode it does this in **its own clone** of this repo, on
a `qa/<TICKET>` branch, and pushes that branch here. A person reviews it and
merges it to `main` like any other test change, through a pull request.

Run a generated spec yourself:

```bash
npx playwright test e2e/qa/TB-601.spec.ts --project=qa-agent --reporter=list
```

The Xray test cases follow the same review: they are committed with the spec, and
exported to Jira only after merge. See [xray/README.md](xray/README.md).

Generated specs are a starting point, not a verdict. Read them before merging.
A test that fails because it guessed a selector is a fix for the spec. A test
that fails on correct selectors is a finding for the ticket.

## Search suite

Playwright suite for the NL search feature, driven entirely against the
deployed portal (`https://tripbuilder-portal-gmguhndwguh2fxh6.a03.azurefd.net`)
— no localhost dev servers required.

### Structure (POM)

- `e2e/pages/` — page objects: `LandingPage` (Auth0/Entra sign-in),
  `SearchLandingPage` (`/slp` client-brief input), `SearchResultsPage`
  (`/srp` results + edit-brief).
- `e2e/utils/search-interception.ts` — `submitSearchAndCapture()`: drives
  the UI submit and captures the real
  `POST .../bff/api/tripagents/chat/pim-itinerary-search` response in one
  call, so a test can assert on both rendered cards and raw payload.
- `e2e/ui/search.spec.ts` — one UI+API smoke test through the real portal.
- `e2e/api/pim-itinerary-search-positive.spec.ts` +
  `e2e/api/fixtures/pim-search-positive-dataset.csv` — hand-authored,
  data-driven, API-only coverage (no browser) looping every dataset row
  against the BFF directly, asserting `interpretedQuery` accuracy
  (destination label/localeType, duration, budget tier) and result
  relevance. Every row here expects a real, resolvable destination and a
  non-empty result set. Add scenarios by adding CSV rows — no code changes
  needed.
- `e2e/api/pim-itinerary-search-negative.spec.ts` +
  `e2e/api/fixtures/pim-search-negative-dataset.csv` — the zero-results
  counterpart: queries that isolate one facet no live product can satisfy
  (destination, budget, group size), plus a budget+groupSize combination
  row. This CSV is **generated**, not hand-authored (see globalSetup
  below) — gitignored, and the whole spec is skipped when it hasn't been
  generated (off-VPN runs).
- `e2e/traveler/` — **not search coverage.** DB ground-truth checks for
  make-payable's outbound `TravelerInfoIntegrationEvent`
  ([TB-271](https://traveledgelab.atlassian.net/browse/TB-271)), with its
  queries kept as runnable `.sql` files shared with DBeaver and the
  `tb-271-verify` CLI. Its own `traveler` Playwright project — no browser, no
  `setup` dependency — and it skips entirely unless
  `MAKE_PAYABLE_POSTGRES_URI` is set, so `npm run e2e` stays green off-VPN.
  See `e2e/traveler/README.md`, which is explicit about what it does **not**
  cover (the Service Bus hop, and the UI trigger itself).
- **Grouping:** both specs bucket their rows into nested `test.describe`
  blocks by the facet/facet-combination each row isolates — `category` for
  the positive dataset (`pax-phrasing`, `granularity-state`, `currency`,
  `template-phrasing`, …), `facetsUnderTest` for the negative one
  (`destination(country)`, `budget`, `budget+groupSize`, …). The positive
  CSV is physically laid out the same way on disk (blank-line-separated
  blocks, same order as the describe tree), via `groupBy()` in
  `e2e/helpers/csv.ts`, so the file and the report read the same. Add a new
  category by giving a row that `category`/`facetsUnderTest` value — no
  code changes needed, the describe blocks are derived from whatever values
  are present.
- **Curl reproduction:** every test attaches a ready-to-run `curl` command
  (method, URL, headers incl. the session `Cookie`, and JSON body) to its
  Playwright report entry — see `e2e/helpers/curl.ts`. Useful for handing a
  specific row to someone without repo access, or replaying a query outside
  the test run. The api project's `APIRequestContext` doesn't expose what
  it actually sent, so the cookie is reconstructed straight from
  `AUTH_STATE_PATH` (same file the request context itself was seeded from)
  rather than intercepted — accurate as long as that file is current.
- `e2e/auth.setup.ts` — the `setup` project; see Auth below.
- `e2e/global-setup.ts` — Playwright `globalSetup` prehook that runs once
  before every `playwright test` invocation, orchestrating two live-
  inventory-derived regenerations (both require `PIM_MONGODB_URI`,
  VPN-only — same as the DB ground-truth checks below; each skips
  gracefully, logging a warning and leaving any existing fixture in
  place, when it's unset):
  - `e2e/utils/live-inventory.ts` — queries `marketplace.product-live-search`
    (distinct countries, logged to console → per-country flat read),
    cross-database merged with `stockroom.products` for
    `MinGroupSize`/`MaxGroupSize`, and regenerates
    `e2e/api/fixtures/live-inventory-dataset.csv` (gitignored) with
    columns: `id`, `DurationDays`, `Theme`, `Style`, `HotelRating`,
    `TravelStyle`, `Services`, `Pricing`, `Currency`, `MinGroupSize`,
    `MaxGroupSize`, `IsFeatured`, `Rank`.
  - `e2e/utils/live-facet-ground-truth.ts` + `generate-negative-facet-dataset.ts`
    — pulls the same distinct countries plus the highest `Pricing.BaseCost`
    and `MaxGroupSize` seen anywhere in live inventory, and uses those as
    the "definitely unsatisfiable" thresholds when generating
    `pim-search-negative-dataset.csv` above — so "budget too high" / "group
    too big" stay true by construction instead of hand-picked magic
    numbers that can go stale as inventory changes. Destination-facet rows
    use fixed fictional place names (Genovia / New Cascadia / San Junipero)
    at the Country/Region/City granularities — Continent is skipped since
    there are only 7 real ones, so a "fake continent" isn't a meaningful
    natural-language test case.

### Xray Cloud reporting

`e2e/reporters/xray-reporter.ts` pushes each run into a single Xray Cloud Test
Execution, with failure evidence attached per test: the failure screenshot,
video and trace (UI project), plus the `assertion-failures` dump and the
ready-to-run `curl` reproduction (both projects).

- **Configure** by filling the `XRAY_*` vars in `.env` (see `.env.example`);
  create the key pair in Jira under *Apps → Xray → API Keys*. Leave them unset
  and the reporter no-ops with a warning — same convention as
  `PIM_MONGODB_URI`, so a run without Xray access is still a full run.
- **Batched:** one authenticate + one `/api/v2/import/execution` per run, not
  per test, so dataset rows are free in Xray round-trip terms.
- **Never fails the run.** An Xray outage warns; the test verdicts stand.
- **Mapping** is by the `xrayKey` column in each dataset CSV, applied via
  `annotateXray()`. A `@KEY-123` tag in a test title works as a fallback. Rows
  with no key are listed at the end of the run as unmapped rather than
  silently dropped. The negative dataset is generated and gitignored, so its
  keys live in the committed
  `e2e/api/fixtures/negative-dataset-xray-keys.json` (row id → issue key) and
  are merged in by the generator.
- **Step-level evidence caveat:** Xray matches the reported `steps` array
  *positionally* against the manual steps defined on the Test issue. These
  specs don't use `test.step()` yet, so each test currently reports one
  synthesized step carrying the whole verdict. To get true per-step pass/fail,
  wrap spec phases in `test.step()` — one per manual step, same order — or set
  `XRAY_STEP_RESULTS=false` to send test-level evidence only.

### Parallelism

The `api` project runs `fullyParallel: true`: it drives no browser and every
row mints its own `sessionId`, so rows are independent. `workers` defaults to
4 and is overridable via `E2E_WORKERS` — the ceiling is whatever rate limit
trip-agents applies, not local CPU. The `ui` project stays `fullyParallel:
false` on purpose: parallel browsers against one portal session multiply flake
without helping, since the bottleneck is agent latency.

`trace` and `video` are both `retain-on-failure` rather than `on-first-retry`
— `retries` is 0 here (an LLM-backed suite that only passes on retry is itself
a finding), so `on-first-retry` would never capture anything.

### Auth

UAT's Auth0 tenant serves a plain email/password form with no MFA step, so
sign-in is fully automated. The `setup` project runs as a dependency of both
`ui` and `api`, refreshes `e2e/.auth/state.json` (gitignored), and both
projects reuse that session for the rest of the run.

1. `cp .env.example .env` and fill in `TBA_E2E_PASSWORD` (never commit `.env`).
2. That's it — `npm run e2e` handles auth itself.

`npm run e2e:auth` runs the setup project on its own, headed, if you want to
watch the sign-in while debugging it.

### Running

```bash
npm install
npx playwright install chromium   # first run only
npm run e2e                       # runs the ui, api and traveler projects
```

Run just one project with `npm run e2e:ui-project` / `npm run e2e:api-project` /
`npm run e2e:traveler`.

The `traveler` project is browser-free and fast (~18s), and it self-skips when
`MAKE_PAYABLE_POSTGRES_URI` is unset — so unlike the LLM-backed suites below,
it is cheap enough to run on every PR.

### Run cadence

The API suite calls a real LLM-backed agent per query — non-deterministic
and slower than a typical smoke test. Run on-demand or on a schedule (e.g.
nightly) when evaluating search quality; it is not intended to gate every PR.
